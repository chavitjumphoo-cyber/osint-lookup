# Use Cases และเกณฑ์ยอมรับ

> ข้อมูลทั้งหมดเป็นข้อมูลจำลอง/ข้อมูลสาธารณะ ไม่ใช้ข้อมูลคดีจริง

## UC-01 ตรวจเบอร์ต้องสงสัยจากสายแจ้งความ

- **ผู้ใช้**: analyst
- **สถานการณ์**: พลเมืองแจ้งว่าได้รับสายจากเบอร์หนึ่งและอ้างเป็นเจ้าหน้าที่
- **ขั้นตอน**: login → กรอกเบอร์ → เลือกความลึก quick → เริ่มสืบสวน → อ่าน carrier/footprint → เปิดรายงาน
- **เกณฑ์ยอมรับ**
  1. ระบบแยกประเภทเป็น `phone` ถูกต้อง
  2. เบอร์ผิดรูปแบบ (เช่น `12ab`) ถูกปฏิเสธพร้อมข้อความ
  3. ทุก finding มีแหล่งที่มาและ hash
  4. รายงานมีข้อจำกัดเรื่อง “ไม่พบ ≠ ปลอดภัย”

## UC-02 ตามรอย username เดียวกันข้ามแพลตฟอร์ม

- **ผู้ใช้**: analyst
- **สถานการณ์**: username เดียวกันปรากฏในกลุ่มขายของออนไลน์และเว็บบริจาค
- **ขั้นตอน**: login → กรอก username → standard/deep → ตรวจ candidate → ยืนยัน/ตัด → pivot ต่อ
- **เกณฑ์ยอมรับ**
  1. ระบบแสดง found / not_found / blocked แยกกัน
  2. identity candidate ต้องผ่าน human review ก่อนสรุป
  3. child run ผูก `parent_run_id`
  4. viewer เปิดดูได้แต่กดยืนยันไม่ได้

## UC-03 ตรวจโดเมนเว็บฟิชชิ่งและออกรายงานส่งต่อ

- **ผู้ใช้**: analyst + admin ตรวจทาน
- **สถานการณ์**: ได้ลิงก์จาก SMS ต้องประเมินก่อนส่งต่อให้หน่วยสืบสวน
- **ขั้นตอน**: login → กรอกโดเมน → ตรวจ DNS/RDAP/Wayback → export JSON/DOCX → admin ตรวจ audit chain
- **เกณฑ์ยอมรับ**
  1. URL ที่ชี้ private IP ถูกปฏิเสธ (SSRF guard)
  2. รายงานมีทุก finding + confidence + limitation
  3. export ตรวจ hash ซ้ำได้
  4. audit chain ยังตรวจผ่านหลัง export

## ตัวชี้วัดความสำเร็จของงาน

- 3 กระบวนการหลักใช้งานได้ครบและมี validation
- 401 เมื่อไม่มี token, 403 เมื่อสิทธิ์ไม่พอ
- ชุดทดสอบ ≥ 8 กรณีผ่านทั้งหมด
- ผู้ใช้ใหม่ทำตามคู่มือแล้วทำงานได้โดยไม่ต้องมีผู้พัฒนาโบกรถ
